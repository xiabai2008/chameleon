# Chameleon 🦎 — 完整开发路线图

> 配套文档：《Chameleon 🦎 — 实战级 AI Agent 爬虫工具开发方案》
> 本文档将方案中的 8 个 Phase 细化为可执行的任务清单，每个任务有明确交付物和验收标准。
> 原则：**测试先行、每阶段可独立交付、先跑通再加固、Agent 接口贯穿始终**。

---

## 阶段总览与依赖关系

```
P0 脚手架 ──► P1 核心引擎 ──► P2 反爬基础 ──► P3 处理管线 ──► P4 高级反爬
                                                              │
P5 深度爬取 ◄─────────────────────────────────────────────────┘
   │
P6 Agent 接口 ◄── P1-P5 全部能力
   │
P7 打磨上线 ──► P8 增强功能（持续迭代）
```

| 阶段 | 内容 | 里程碑 |
|------|------|--------|
| P0 | 工程脚手架 | — |
| P1 | HTTP/Browser 引擎 + 智能路由器 | M1: 静态页 + SPA 页可采集 |
| P2 | 反爬基础（代理/UA/stealth/蜜罐） | M1: 能对抗中等反爬 |
| P3 | 处理管线（清洗/Markdown/提取/校验） | M2: 输出 LLM 友好数据 |
| P4 | 高级反爬（TLS/行为/验证码/升级链） | M2: 6 级升级链运转 |
| P5 | 深度爬取（并发/断点/robots） | M3: 整站采集 |
| P6 | Agent 接口（MCP/REST/CLI/SDK） | M4: Agent 可自主调用 |
| P7 | 打磨上线（Docker/监控/文档） | M5: 生产可用 |
| P8 | 增强功能（API 逆向/搜索/语义提取） | M6: 差异化竞争力 |

## Phase 1：核心引擎 + 智能路由器

**目标**：能采集静态页和 SPA 页，路由器按内容质量自动决策，这是整个系统的心脏。

| # | 任务 | 交付物 | 验收标准 |
|---|------|--------|----------|
| P1-1 | 引擎基类：`BaseEngine.fetch()` 统一接口 + 结果类型 | engines/base.py | 所有引擎实现同一协议 |
| P1-2 | HttpEngine（httpx async）：超时、重定向策略、编码检测（charset-normalizer）、HTTP/2 | engines/http_engine.py | 静态页、301/302、GBK 编码页均正确 |
| P1-3 | BrowserEngine（Playwright）：浏览器池管理、context 复用、`wait_until` 策略、`wait_for` 选择器、cookie 持久化 | engines/browser_engine.py | 本地 SPA fixture 渲染出内容 |
| P1-4 | 内容校验器：状态码 + 长度阈值（<500） + 反爬关键词库（中英文，可扩展） | core/content_validator.py | 403/429/验证码页/短内容判定为无效 |
| P1-5 | SmartRouter：auto 模式（HTTP → 升级 Browser → force_browser 开关）、`_is_valid_content` 决策 | core/router.py | 静/动态页自动分流，行为可日志复现 |
| P1-6 | 重试基础：指数退避 + 重试次数配置 | 并入 router | 网络抖动场景自动重试成功 |

**关键技术点**：
- 浏览器池必须与任务解耦：`BrowserPool` 管理 N 个 context，支持并发任务共享
- 编码检测必须前置：`response.text` 不可信，用 `charset-normalizer` + 响应头综合判断

**测试策略**：
- fixtures：用 FastAPI/Starlette 启动内存测试站点（静态页、SPA 页、反爬页、重定向）
- Playwright 在 CI 用 `playwright install --with-deps chromium`（Linux）或直接 mock

**阶段验收**：两个测试站点 fixture 通过：纯静态页走 HTTP 引擎；`<div id="app"></div>` 的 SPA 页自动升级浏览器引擎拿到真实内容。

## Phase 2：反爬基础

**目标**：中等强度反爬（UA/头/指纹/IP 限制）可对抗。

| # | 任务 | 交付物 | 验收标准 |
|---|------|--------|----------|
| P2-1 | ProxyManager：静态代理列表 → Redis 池；健康检查、评分（zincrby）、淘汰阈值、region 选择 | anti_detection/proxy_manager.py | 代理失效自动降分剔除；region 过滤生效 |
| P2-2 | IdentityFaker：内置 50+ 真实 UA 起步（按浏览器+版本分组）；完整请求头生成（Accept-Language/Referer/Sec-Fetch-*/Accept-Encoding） | anti_detection/identity_faker.py | 同一 URL 连续 5 次请求头各不相同且完整 |
| P2-3 | Stealth：init script 注入（`navigator.webdriver` 隐藏、CDP `Page.addScriptToEvaluateOnNewDocument`）+ `--disable-blink-features=AutomationControlled` | anti_detection/stealth.py | 反爬检测 fixture 通过（可加载 playwright-stealth 对比验证） |
| P2-4 | HoneypotFilter：可见性检测（CSS display/visibility/尺寸 + Playwright computed style），过滤不可见链接 | anti_detection/honeypot_filter.py | 隐藏链接从不被访问 |
| P2-5 | Cookie/Session 管理：httpx 持久 cookie jar + 浏览器 context 复用，Session 池 | infra/session_pool.py | 登录态跨请求保持 |
| P2-6 | 重试中间件：403/429 → 换代理 + 换 UA + 退避重试；retry 后仍失败标记 `BlockedError` | core/middleware/retry.py | 模拟站 403 场景：换代理后成功 |

**关键技术点**：
- playwright-stealth 维护状态堪忧（2023 年后基本停滞），P2-3 的注入脚本必须**自研兜底**，第三方库仅作对照验证。自研方案：CDP 注入 + 常用属性清理清单
- 代理评分阈值可配置（默认 30 分起，失败 -10，成功 +2），初始分 50

**测试策略**：自建"反爬模拟站" fixture（对 403 请求计数、检查 UA/头完整性、隐藏链接陷阱、Cookie 校验），每次任务断言模拟站侧的状态。

**阶段验收**：模拟站从"裸请求必被 403"变为"自动换代理+UA 后成功"；蜜罐链接 0 次访问；行为日志完整。

## Phase 3：处理管线

**目标**：原始 HTML → 干净的、LLM 友好的、可选结构化提取的输出。

| # | 任务 | 交付物 | 验收标准 |
|---|------|--------|----------|
| P3-1 | Cleaner：去 script/style/nav/footer/ad 节点 + readability 主内容提取（先评估 readability-lxml / 自研） | pipeline/cleaner.py | 文章页：正文完整，导航/评论/广告剔除 |
| P3-2 | Converter：HTML → Markdown（markdownify），相对路径转绝对 URL，表格/代码块保留 | pipeline/converter.py | 样例页 markdown 干净、链接可点 |
| P3-3 | FitMarkdown：按 token 预算裁剪（优先保留标题/首段/高信息密度段落），参考 Crawl4AI Pruning/BM25 | pipeline/converter.py | 超长页裁剪到预算内，核心信息不丢 |
| P3-4 | CssExtractor：selectolax + JSON Schema（多字段、嵌套、列表） | pipeline/extractors/css_extractor.py | 同构列表页提取正确率 ≥ 95% |
| P3-5 | XPathExtractor：lxml 实现，同一 Schema 接口 | pipeline/extractors/xpath_extractor.py | 与 CSS 提取结果一致 |
| P3-6 | LLMExtractor：BYO-LLM，LiteLLM 兼容层（多厂商切换），prompt 模板 + JSON 输出约束 | pipeline/extractors/llm_extractor.py | mock LLM 返回结构化 JSON 并校验通过 |
| P3-7 | Hybrid 模式：LLM 分析 1-2 个样本生成 CSS Schema → 批量 CSS 提取 → 质量漂移检测 → 触发重新生成 | pipeline/extractors/hybrid.py | 批量页提取成本大幅低于全 LLM |
| P3-8 | Validator：Pydantic schema 校验、缺失字段报告、类型强制 | pipeline/validator.py | 坏数据被标记而非静默通过 |
| P3-9 | Deduplicator：URL 规范化 + simhash 内容指纹 | pipeline/deduplicator.py | 重复内容被识别 |
| P3-10 | ScrapeResult 组装：status/content{markdown,html,raw_html}/extracted/metadata/links/images/error 统一输出 | core/models.py + pipeline | 输出结构与方案 6.4 完全一致 |

**关键技术点**：
- **先过滤再提取**（Crawl4AI 精髓）：LLM 提取前先走 Cleaner + FitMarkdown，token 成本降 10 倍
- 提取策略用抽象基类 `BaseExtractor`，新增策略不改核心
- links/images 提取用 selectolax 一次性遍历，避免多次解析

**阶段验收**：真实博客文章页输出干净 markdown；列表页用 Schema 提取出完整结构化数据；token 裁剪生效。

## Phase 4：高级反爬

**目标**：TLS 指纹、行为模拟、验证码、6 级自动升级链。

| # | 任务 | 交付物 | 验收标准 |
|---|------|--------|----------|
| P4-1 | curl_cffi 引擎：TLS 伪装（impersonate 参数），作为 HttpEngine 的 stealth 变体 | engines/http_engine.py（stealth 模式） | TLS 指纹检测 fixture 通过（curl 指纹法验证） |
| P4-2 | 升级链状态机：Level 0-6 完整实现，每级失败原因分类（403/429/内容异常/验证码/超时），逐级记录日志 | core/escalation.py | 状态机可单测：给定失败序列，升级路径正确 |
| P4-3 | 行为模拟：请求间隔正态分布（2-10s 可配）、滚动模拟（增量滚动+内容去重）、停留时间 | anti_detection/behavior_simulator.py | 行为特征分布符合配置 |
| P4-4 | 鼠标轨迹模拟（Playwright mouse 序列：移动+停留+点击） | anti_detection/behavior_simulator.py | 轨迹回放通过行为检测 fixture |
| P4-5 | CaptchaRouter：类型检测（图片/滑块/文本）→ ddddocr 简单验证码 → 第三方 API（CapSolver/2Captcha，可插拔）→ 失败上报 `CaptchaRequiredError` | anti_detection/captcha_solver.py | 模拟验证码 fixture 走通识别链路 |
| P4-6 | 无限滚动加载：自动滚轮 + 内容指纹去重判定到底 | engines/browser_engine.py | 滚动列表页抓全 |
| P4-7 | Shadow DOM / iframe 穿透：`shadow_root` 递归遍历、iframe 自动切换 context | engines/browser_engine.py | Shadow DOM fixture 内容可提取 |
| P4-8 | WebSocket 拦截（CDP Network domain），提取增量数据 | engines/browser_engine.py（可选增强） | WS 推送 fixture 可捕获 |

**关键技术点**：
- 升级链是**可观测的**：每次升级写入 metadata（engine 层级、失败原因、耗时），Agent 可据此判断信任度
- Level 6 验证码失败 ≠ 任务失败：返回 `captcha_required` 状态 + `suggested_action`（换代理重试 / 人工打码），由 Agent 决策
- ddddocr 只处理简单数字/字母验证码，滑块和 reCAPTCHA 直接路由第三方，不做无谓尝试

**测试策略**：自建"高强度反爬模拟站"：JS 挑战（5 秒盾模拟）、行为分析（记录轨迹）、TLS 指纹检测（可选 tlsfingerprint.io 自托管版）、验证码。

**阶段验收**：升级链从 Level 0 自动爬到成功（不同 fixture 停在合理层级）；验证码流程返回正确状态码；全过程日志可回放。

## Phase 5：深度爬取

**目标**：整站采集：URL 发现、并发控制、断点续爬、合规。

| # | 任务 | 交付物 | 验收标准 |
|---|------|--------|----------|
| P5-1 | URL 发现：a 标签提取 + sitemap.xml 解析（含 gzip sitemap index） | crawler/url_discovery.py | 本地 50 页站点发现完整 |
| P5-2 | UrlFilter：同域限制、include/exclude 模式、扩展名黑名单、URL 参数规范化去重、fragment 去除 | crawler/url_filter.py | 过滤规则可组合，误杀率为 0 |
| P5-3 | DeepCrawler：BFS / DFS / Adaptive（信息觅食：高链接密度优先） | crawler/deep_crawler.py | 三种策略均可跑通 |
| P5-4 | 并发控制：每域名令牌桶限速 + 全局信号量，配置独立 | crawler/rate_limiter.py | 域 A 高压不拖累域 B |
| P5-5 | 任务调度：arq（asyncio 原生，优于 Celery）或 Redis + 原生 asyncio——**P5-5a 做选型 ADR** | crawler/scheduler.py | 任务状态机 queued/running/done/failed 正确 |
| P5-6 | 断点续爬：任务持久化（已爬 URL 集合、待爬队列、失败记录）到 Redis | crawler/scheduler.py | kill -9 后重启任务，无重复无遗漏 |
| P5-7 | robots.txt 解析：缓存、User-Agent 匹配、sitemap 引用 | crawler/robots.py | 禁爬路径不访问（可配置忽略） |
| P5-8 | 增量采集：ETag / Last-Modified 缓存头，只抓变更 | crawler/deep_crawler.py | 二次运行请求数大幅下降 |
| P5-9 | Webhook 回调：任务完成/失败通知（预留 P6 使用） | crawler/scheduler.py | mock webhook 收到事件 |

**关键技术点**：
- 任务队列选型建议直接 `arq`（asyncio 原生）或自研 Redis 列表队列，**不要引入 Celery**——它和 asyncio 引擎存在线程模型冲突
- 断点续爬的原子性：URL 先标记"已分配"再处理，完成后标记"已完成"，避免重复
- Adaptive 策略的评分函数：链接密度 + 深度惩罚 + 内容长度，权重可配

**阶段验收**：本地 50 页站点（含死链、外链、重复 URL）完整爬取，无重复请求；模拟中断后恢复正确；robots.txt 规则生效。

## Phase 6：Agent 接口

**目标**：MCP Server（主）+ REST API + CLI + Python SDK，Agent 零胶水调用。

| # | 任务 | 交付物 | 验收标准 |
|---|------|--------|----------|
| P6-1 | 服务门面 `Chameleon` 类：scrape / crawl / map / extract / search / batch / screenshot / diagnose / check_proxy / get_job_status / get_robots_txt / get_network_log 全部能力收敛 | interfaces/sdk.py | 单入口，参数即文档 |
| P6-2 | MCP Server（FastMCP）：12 工具注册，inputSchema 精确（enum/format/description 齐全），stdio 模式 | interfaces/mcp_server.py | 客户端工具列表 = 12 个 |
| P6-3 | MCP Server：Streamable HTTP / SSE 模式（挂载 FastAPI 共享端口）+ OAuth/API Key 认证 | interfaces/mcp_server.py | 远程可访问且鉴权生效 |
| P6-4 | MCP 输出规范化：统一 `{status, data, error, suggested_action}`，结果 token 预算裁剪（超长自动 FitMarkdown） | interfaces/mcp_server.py | 超长页不撑爆上下文 |
| P6-5 | REST API（FastAPI）：10 端点与 MCP 工具一一对应，同步/异步（job_id）双模式，API Key 认证 + 速率限制（Token Bucket）+ OpenAPI 文档 | interfaces/rest_api.py | 端点全测通，未授权 401 |
| P6-6 | WebSocket 实时进度推送（异步任务） | interfaces/rest_api.py | 客户端收到进度流 |
| P6-7 | CLI（typer）：scrape/crawl/map/extract/search/screenshot/proxy 命令，退出码 0-3，JSON/Markdown 输出切换 | interfaces/cli.py | 端到端命令可跑，退出码正确 |
| P6-8 | SSRF 防护：URL 校验 + 内网 IP 拦截（127/10/172.16-31/192.168/localhost/169.254）+ DNS 解析后二次校验 | interfaces/security.py | 内网地址请求被拒绝 |
| P6-9 | 审计日志：who/when/what/result 全记录 | interfaces/middleware.py | 每次调用可追溯 |
| P6-10 | 集成测试：MCP 客户端 mock 调用全工具；REST 用 httpx 全端点测试；CLI 端到端 | tests/test_interfaces/ | 三个接口层行为一致 |

**关键技术点**：
- 三个接口层**共享同一服务门面**，接口只是"外壳"，核心逻辑不复制
- MCP 工具 `description` 必须写"何时使用/何时不使用"（如 scrape_url vs search_web 的边界），这是 Agent 正确选工具的关键
- REST 异步任务与 P5 调度器打通：`POST /api/v1/crawl` → 入队 → `GET /jobs/{id}`

**阶段验收**：在 Claude Code / opencode 中配置 `mcp_config.json` 指向本服务，Agent 用自然语言"抓取 XX 网站的产品价格"能自主完成 diagnose → scrape/extract 全流程。

## 贯穿性工程实践（所有阶段强制）
